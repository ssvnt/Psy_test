## 18. Неблокирующий контроль качества — P0

### 18.1. Принцип

**QA не прекращает генерацию остальных независимых частей из-за языковой ошибки отдельного поля.** Каждый сгенерированный raw/checkpoint сохраняется до проверки и не перезаписывается. Для замечания создаётся отдельная транзакционная задача исправления.

Основной маршрут:

`SAVED_CHECKPOINT → DETECT → CLASSIFY → LOCAL_REPAIR → REVALIDATE → ACCEPT`

Если локального исправления недостаточно:

`EDITOR_PENDING → EDITOR_PATCH (GigaChat) → REVALIDATE → ACCEPT`

Если в утверждённых пределах не удалось отредактировать:

`FIELD_REGENERATION_AUTHORIZATION → REGENERATE_ONLY_FIELD → REVALIDATE → ACCEPT`

Если бюджет или лимит попыток исчерпан:

`APPROVED_TEXT_BANK_FALLBACK → REVALIDATE → ACCEPT` **либо** `OWNER_ATTENTION_REQUIRED`.

Критическая ошибка достоверности блокирует *публикацию*, не уничтожая сохранённые куски и не превращая весь заказ в безвозвратный `FAILED`.

### 18.2. Поток генерации и проверки

1. Для каждой части получаем `request_identity`, оригинальный RAW, provider receipt, attempt ledger и immutable checkpoint с SHA-256.
2. Независимую часть сразу ставим на QA после сохранения; генератор не ждёт окончательного завершения стилевой редактуры прошлой части.
3. Часть без замечаний фиксируем `QA_LANGUAGE_PASS`.
4. Для отклонённого листового `expert_####` фиксируем точный идентификатор поля, SHA исходного текста, версию сканера и машинный код нарушения. Сам текст не выводим в операционные журналы/MAX.
5. Сначала применяем *одну* детерминированную локальную нормализацию: CRLF, Unicode-пробелы, табуляцию, технические пробелы. Запрещены скрытые изменения чисел, отрицаний, фактов, JSON-ключей, родительских ответов и экспертных оценок.
6. После локальной правки реальный `humanizer-ru` и `pishi-normalno` выполняются повторно; локальный код не вправе утверждать их PASS без фактического запуска.
7. Содержательную *редактуру языка* выполняет отдельный GigaChat-редактор (в пределах разрешённого бюджета). Ему передаётся только проблемное поле, его смысловой исходник, требуемые факты, цель раздела и машинные коды ошибок. DeepSeek остаётся **основной моделью первичной генерации**.
8. Если редактирование не помогло, отдельная регенерация **только проблемного поля** возможна после авторизации расходов и проверки provider receipt. Ни при каких обстоятельствах не инициировать безлимитный повтор всего отчёта.
9. Если проверенный банк текстов содержит строго соответствующий профиль, можно построить fallback с теми же обязательными проверками. Отсутствие подтверждённого fallback — статус owner-attention, не фальшивый PASS.
10. По изменении полей создаётся новая **производная версия** отчёта с собственным SHA; исходные raw/checkpoint остаются неизменными.
11. Полный повторный QA проверяет все связанные поля, структуру, числовые значения и языковые сканеры. Только успешный итоговый допуск + утверждение владельцем разрешают публикацию.

### 18.3. Независимые очереди и остановки

Использовать независимые очереди `generation`, `qa_scan`, `qa_repair_local`, `qa_repair_editor`, `field_regenerate`, `private_render`, `owner_review`, `publication`, `customer_delivery`, `owner_max`. Отсутствие обработчика одной очереди не уничтожает intent других.

Для каждого шага хранить `generation_identity`, `field_id`, `attempt_id`, `original_sha256`, `candidate_sha256`, `qa_policy_sha256`, `event_key`, `state`, `failure_code`, `retry_not_before`, `owner_attention`. Никаких ФИО и текста ребёнка в метриках/владельческих уведомлениях.

### 18.4. Ограничения стоимости и времени

- Любой платный вызов предваряется durable reservation в **отдельном** соответствующем журнале (основная генерация и редактор расходуются отдельно, но общий потолок также обязателен).
- Любой неполный SSE/timeout после возможной отправки — `BILLING_UNKNOWN`; он **не** приравнивается к бесплатной попытке. Нужна сверка по криптографически связанному receipt. Восстановление на основе сохранённого RAW не вызывает модель заново.
- Доказанный presend failure/бесплатный 429 может повторяться только ограниченно и с backoff, без списания за первый запрос.
- Достигнутый бюджет никогда не увеличивается автоматически. Сначала approved fallback, затем owner-attention.
- Проверки языкового качества и локальная сборка не вправе добавлять платные запросы сами.
- Нельзя бесконечно обрабатывать один и тот же `retry_at`: конечное число попыток, durable cursor/lease и конкретный `failure_code`.

### 18.5. Сборка и публикация

Приватный HTML/PDF может собираться заранее из версии `Report JSON vN`, но это **черновик без доступа клиента**. При изменении текста создаются новые артефакты для `vN+1` с SHA и неизменяемым identity. Публикация требует final fact/schema/language PASS + owner review + payment binding + неизменённые артефакты. Никакая стилистическая проблема сама по себе не должна приводить к удалению предыдущих принятых фрагментов.

### 18.6. Критерий для Гарднера 106

Исторический снимок: 61/61 генерационных частей, 67 попыток, 51/181 языковых замечаний QA. Позднее сообщалось о локальном устранении 48 замечаний с остатком 3: это **не новый проверенный серверный снимок**, поэтому RC2 сначала читает актуальные QA/checkpoint receipts и никогда не исходит из предположения, что осталось ровно 3 поля. Не менять сессию 105, не регенерировать все 61 часть.

События для владельца: `QA_REPAIR_STARTED`, `QA_REPAIR_COMPLETED`, `QA_REGENERATION_REQUIRED`, `QA_FALLBACK_APPLIED`, `QA_OWNER_ATTENTION`, `REPORT_ARTIFACTS_READY`. Каждое событие имеет отдельную квитанцию MAX с реальным статусом отправки, не `scan=delivered`.

## 19. Политика QA v1.1 — приоритет над смысловым аудитом из §18

### Проверки, которые остаются обязательными

1. Корректность шкал и числовых результатов теста.
2. Точное соответствие шкал исходному, неизменённому JSON тестирования.
3. Неизменность чисел, отрицаний, структурно закреплённых фактов и иных защищённых значений при редактуре.
4. Структура JSON, обязательные ключи и типы.
5. Фактическое выполнение `humanizer-ru` и `pishi-normalno`.
6. Технические ошибки Unicode, пунктуации, оформления и следы технических маркеров.
7. Защита от разглашения детских данных, целостность checkpoints и публикационных SHA.

### Смысловые оценки, которые НЕ выполняет автоматический валидатор

- «Достаточная глубина» свободной интерпретации, `DEPTH_REVIEW` и аналоги.
- Психологическая убедительность выводов.
- Субъективное качество выбора кружков, профессий и занятий.
- Логическая и литературная связность описательных разделов.
- Субъективные ожидания от текста.

**Разграничение:** отсутствие смысловой оценки ≠ разрешение менять числа или создавать новые необоснованные факты. Редактору дано требование сохранять смысл; автоматический защитный gate проверяет доступные жёсткие инварианты. Если сохранность смысловой информации не может быть надёжно доказана, задача передаётся владельцу, а не получает фиктивный `PASS`.

### Редактор

Редактор GigaChat получает только разрешённые поля и конкретные языковые ошибки, не переписывает остальные части. Счётчик редакторских запросов, бюджет, receipt и классификатор транспортных проблем независимы от основной генерации. Повторные попытки ограничены; ошибка редактора не сбрасывает сохранённое содержание. После реального QA PASS продолжается подготовка HTML/PDF.

### Важное противоречие, разрешаемое этим документом

В §18 старое выражение «глобальный смысловой аудит» разрешено только в виде проверки жёстких, объективных инвариантов исходного JSON/чисел/структуры. **Смысловая субъективная оценка из процесса автоматического QA исключается по явному приоритету §19.**

## 20. Что этот документ НЕ подтверждает

Это архитектурное требование, а не факт внедрения. Не подтверждены рабочие Laravel-очереди редактуры, интеграция с реальным GigaChat, валидная тарифная модель, доступность текстового банка, SMTP/MAX-квитанции и корректные production-маршруты публикации. До их тестирования флаги RC2 не включать и сайт не менять.
